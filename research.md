# Duplicate / Overlapping Responsibilities
- **Background remote delivery**: [`src/background/task.ts`](/Users/mennojongejan/projects/bubbles-notifications-expo/src/background/task.ts:15) + [`src/background/handle-background-notification.ts`](/Users/mennojongejan/projects/bubbles-notifications-expo/src/background/handle-background-notification.ts:113) and [`src/background/firebase-message-handler.ts`](/Users/mennojongejan/projects/bubbles-notifications-expo/src/background/firebase-message-handler.ts:24) are both active. Expo handles a `NotificationTaskPayload`, posts delivery statuses, and schedules a local notification. Firebase handles a `RemoteMessage` and schedules a local notification for data-only pushes, skipping when display content already exists.
- **Can both run for one event?** Uncertain. The repo does not contain an end-to-end proof, but both are always registered via [`src/background/setup.ts`](/Users/mennojongejan/projects/bubbles-notifications-expo/src/background/setup.ts:1), and the shared local scheduler dedupes by `notificationId`/payload for 5 seconds in [`src/notifications/local-notification.ts`](/Users/mennojongejan/projects/bubbles-notifications-expo/src/notifications/local-notification.ts:11), which strongly suggests the code expects duplicate scheduling attempts.
- **Possible effects**: duplicate background callbacks and duplicate local-scheduling attempts are plausible; duplicate click analytics are not, because the Firebase path does not post analytics; platform divergence is real, because the Expo task has Android-specific tap-payload skipping and richer status reporting.
- **Primary vs redundant**: Expo looks like the richer primary implementation for Bubbles-specific behavior, while Firebase looks like the transport-specific compatibility layer. One of them should become redundant long-term, but this repo alone does not prove which one can be removed safely today.

# Intentional Separation of Responsibilities
- **Foreground receive vs foreground display** is intentional and good: Firebase receives the remote message in [`src/runtime/foreground-message-observer.ts`](/Users/mennojongejan/projects/bubbles-notifications-expo/src/runtime/foreground-message-observer.ts:20), then Expo displays it locally and applies presentation policy in [`src/notifications/local-notification.ts`](/Users/mennojongejan/projects/bubbles-notifications-expo/src/notifications/local-notification.ts:138) and [`src/runtime/notification-handler.ts`](/Users/mennojongejan/projects/bubbles-notifications-expo/src/runtime/notification-handler.ts:21).
- **Permission vs token ownership** is intentional and good: Expo owns permission state/requesting, while Firebase owns FCM registration/token retrieval. That matches the current code cleanly.
- **Android default-channel config** is intentional: the Expo plugin configures default channel/icon/color, and [`plugin/src/with-firebase-messaging-manifest.ts`](/Users/mennojongejan/projects/bubbles-notifications-expo/plugin/src/with-firebase-messaging-manifest.ts:30) mirrors channel/color metadata for Firebase-delivered notifications so both native paths use the same defaults.

## Target Architecture
- **Option A — Prefer `expo-notifications`**: move canonical token ownership to Expo APIs and use Expo as the only notification-facing package. Advantage: one package. Disadvantage: current code hardcodes `tokenType: 'fcm'` and also sends Firebase Installation ID, so iOS token semantics and backend contracts would change. Complexity: High. Risk: High.
- **Option B — Prefer `@react-native-firebase/messaging`**: make Firebase the sole remote-delivery owner and move background analytics into that path. Advantage: matches the current FCM-first backend contract. Disadvantage: Expo is still needed for permissions, channels, local display, and tap handling unless you replace those too. Complexity: High. Risk: High.
- **Option C — Keep both with strict responsibilities**: Expo owns permissions, channels, local scheduling/presentation, and tap/open handling; Firebase owns FCM token retrieval plus foreground/background remote receipt; Installations owns FID. Then remove one background receiver after migrating missing behavior. Advantage: smallest behavior change and matches the actual codebase. Disadvantage: still two dependencies. Complexity: Medium. Risk: Medium.

Recommended: **Option C**, specifically “Firebase owns transport, Expo owns UX.” The current backend contract is explicitly FCM-shaped, Expo token APIs are unused, and the only meaningful overlap to fix is dual background receipt.
